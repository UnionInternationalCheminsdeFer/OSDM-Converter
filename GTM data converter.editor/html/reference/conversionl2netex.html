Conversion details IRS 90918-10 to NeTEx

The export is still experimental aund not fully tested.

Export Files

The export is splitted into multipe files as the NeTEx data model consumes too much Heap Space otherwise. The Split is done according to the first letter of the start station of a regional validity.

Mappings

Mapping of Carriers accepting the fare:

Carriers --> TransportOrganisation
Carrier Groups --> GroupOfOperators
Carriers accepting a fare --> FareStructureElement (with type efp:accepted_by) --> GenericParameterAssignment --> Limitations --> ValidityParameters --> GroupOfOperators

Mapping of the route:

Station ---> Stop Pace
Station Set used in a Route --> Zone including a list of Stops
Route --> FareStructureElement --> DistanceMatrixElement --> SeriesConstraint --> itineraray
The textual itinerary description includes the textual description of the route. It uses a DistanceMatrixElement although it is not a distance matrix for price calculation. Unfortunately there is no way to include structured data for the route. The SeriesConstraint looks as if someone tried to include the outdated TAP-TSI B.1 in the model but that failed and the result is unusable.

Mapping of the service class:

ServiceClass --> ClassOfUse
ServiceClassConstraint --> FareStructure Element --> ClassOfUse

Mapping of Service brands:

ServiceConstraint --> FareStructure Element --> GenericParameterAssignment --> Limitations --> UsageParameter --> BrandingRef

Mapping of the validity for travel:

TravelValidity --> FareStructureElement of type travel including a GenericParameter with the duration. KeyValues are need to cover the cases used in Rail.

Mapping of the availability to sell:

SalesAvailability --> FareStructureElement --> GeneralParameterAssignment including LimitationGroups with PurchaseWindows

Mapping of the reduction cards:

Reductions -> EntitlementProduct
The entitlement product is included with basic parameters only, as it is not intended to sell the entitlementproduct (It might even be from another provider). Unfortunately NeTEx does not distinguish between the Entitlement as a product and the Entitlement as reference for a reduction.
Link of a Fare to a Reduction --> FareStructureElement --> GeneralParameterAssignment --> LimitationGroup --> EntitlementRef
The short name of a reduction card used in a barcode can be added as short name as a workaround.

Mapping of Passenger Constraints:

Passenger Constraint --> FareStructureElement --> UserProfile --> PassengerType, age limits
The predefined passenger types or NeTEx are incomplete, but proprietary types can be defined as a workaround (Type: Other, using a proprietary text). This needs to be done for bicycles and dogs.
Free companions are added in the user profile as companion profiles with DiscountBasis = FREE.
Combination restrictions are added to the User profile as companion profiles with discount Base NONE. A similar restriction for LuggageAllowance is missing, as workaraound the companion restriction includes the ref of the luggage allowance (e.g. limit the number of dogs).
Bicycles and dogs are defined as LuggageAllowance. However a code for dos is missing. A KeyValueList is used to add the missing code
.

Mapping of Group Limits:

Limits for group sizes are matted to:
FareStructureElement --> GenericParameterAssignment --> GroupTicket.
The passengers relevant to the count of the group size are listed in:
GenericParameterAssignment --> Limitations --> UsageParameterRef
It is not possible to express special group size rules where passenger types do not count equally (e.g. children count as half of an adult. Such rules have been applied until recently and might still exist in some domestic tariffs.

Mapping of a single Fare:

Fare --> PreassignedFareProduct including:
Reference to the Sales API --> PricingEngine (defined as URI, but needs to be a symbolic indicator)
References to the above defined FareStructureElements
Link to service class via AccessRightInProduct
ConditionSummary (The semantics of the booleans is not clearly defined)

Mapping the Price:

Unfortunately there is no option to link a price to the FareProduct directly which would be the natural way of modelling (Note: Refund and Exchange fees can be linked to the FareProduct directly!). The link hast to be indirect via a FareTable:
Price of a Fare:
FareFrame --> FareTable (Price) --> FarePrice
FareFrame --> FareTable --> FareProductPrice incl. Reference to the FareProduct and FarePricec

Mapping of Fulfillment Requirements:

Fulfillment requirements have no mapping in NeTEx. The content might be mapped to TypeOfTravelDocument with a reference to the fare product located in a SalesOfferPackageElements. The elements provided in TypeOfTravelDocument are mainly useless as they specify the media only and not the content standard to be used (barcode standards, central registries). All the content has to be mapped in KeyValues. The TypeOfMachineReadability can be used, but the content refers to the graphical encoding standards only, not to the more relevant encoding standards of the barcode content.

Mapping of After Sales conditions:

After sales rules are mapped to Fare Structure Elements including the conditions of a fare product as Refunding and Exchanging objects. Note: The elements to define the time intervals of the after sales rules are in the abstract Reselling Object (!This does not mean reselling, it is just the abstract After Sales Object!). Unfortunately, the common time interval elements are named exchange, but used for refund as well.

Missing Mappings due to missing concepts in NeTEx


The route can be included in NeTEx as textual description only. NeTEx is lacking a concept of regional validity that is flexible enough to describe the routes.
NeTEx does not include any concepts to describe the rules of combining fares between different providers.
The description of reductionCards as Entitlements does not provide the option to define combined cards.
VAT split of the price is missing.

Missing Mappings due to missing concepts in NeTEx with workaround


The carriers accepting a specific fare are missing in NeTEx. They can be included using a generic FareStructureElement with a specific type defined in the profile: efp:acceptedby.
Missing passenger types: define proprietary types with type “OTHER”. Naming conventions need to be agreed bilaterally. The standard OSDM types are added as KeyValues.
There is no direct link from a fare product to a price. A workaround can be used by defining a a fare table with FareProductPrice linking price and fare product. This can be done but adds unnecessary complexity. Moreover it is inconsistent as the Refund and exchange fees can be attached to the FareProduct.
ReductionCards referenced for reductions need to be included as EntitlementProduct. The reductionCard as a reference might be indicated by the missing link to a price of the EntitlementProduct.
The UsageValidityTypeEnumeration does not provide the required values. A KeyValueList is used to provide the values from OSDM.
Restrictions to Service Brands are modelled as UsageParameters containing a branding only, there seems to be no concept of restrictions to brands.
The concept of assigning sales APIs at the price level is extremely inefficient. More advances concepts would assign stations or regions to a sales engine.
Fulfillment requirements are not modelled in NeTEx and need to be added via KeyValues in TypeOfTravelDocument and TypeOfMachineReadability.
The code for dog in luggage allowance is missing. A KeyValueList is used to provide the code of OSDM. The user profile does not allow limits on LuggageAllowances. The Reference to the LuggageAllowance is used in the CompanionProfile as workaround.
